# BT — Overlay System

Banjo-Tooie makes heavy use of **dynamically loaded code overlays** — the
largest complicating factor for a static recomp. Overlays are code banks
loaded into a fixed 0x80800000 VRAM region at runtime.

## `overlays.us.toml`

Lists every overlay and its entrypoints as a TOML array-of-tables keyed
`overlay`. ~850 named overlays (plus empty slots), e.g.:

```toml
empty = true

name = "gsmaker"
entrypoints = [
  "gsmaker_entrypoint_0",
  ...
  "gsmaker_entrypoint_25",
]

name = "anseq"
entrypoints = [ "anseq_entrypoint_0", ... ]
```

In the real file each entry is nested under the TOML array-of-tables key
`overlay` (written as `[` `[overlay]` `]` in the raw TOML, which the snippet
above omits for brevity). `empty = true` marks a gap slot in the on-disk
table.

## Where the overlay table is built

The Makefile builds overlay headers via `overlay_processor`:

- generates `assets/overlay_table.s` (ROM offsets of each overlay),
- generates `assets/overlays/<name>/<name>_header.s` — 16-byte-size header
  describing text/rodata/data/bss sizes, entrypoint count, reloc count,
  name, relocs.

Overlay header format (from `overlay_processor.cpp`):

```text
uint16 text_size / 16
uint16 rodata_size / 16
uint16 data_size / 16
uint16 bss_size / 16
uint16 entrypoint_count
uint16 reloc_count
uint8  flags byte (0x80 = compressed)
uint8  name length
...
uint32 entrypoints[]  (offset in overlay vram)
char   name[]
uint16 relocs[]
```

## Overlay VRAM / entrypoints

- Overlays remap to `0x80800000` (`overlay_vram`), so entrypoint addresses
  are `0x80800000 + offset`.
- `syscall_symbol_addrs.us.txt` builds the runtime syscall/overlay dispatch
  table (`overlay_syscalls.s`) — generated by `tools/syscall_builder`
  (see [Syscalls](syscalls.md)).
- Compressed overlays carry a `0x80` flag and zlib payload
  (see [Compression](compression.md)).

## TooieRecomp runtime (P06)

Static recomp does **not** execute MIPS at `0x80800000`. Each overlay section is
recompiled to native functions; entrypoints are named without the core2 `_`
prefix (`gcstatusDll_entrypoint_0`).

- Syscall trampolines in core2 are handled by `recomp_syscall_handler` (see
  [Syscalls](syscalls.md)): decode stub from ROM → dispatch table → host
  `ovl_load` → alias temporário no link VRAM `0x80800000` → native call.
- Dispatch table generation: `TooieRecomp/tools/generate_overlay_dispatch.py`
  (index order from `overlays.table.toml`, rom/size from `recomp_overlays.inl`).
- Do **not** use N64Recomp `overlay_sections_by_index` as game overlay indices
  (alphabetical relocatable list).
- Fixed-bank boot loaders that inflate compressed carts are overridden for the
  **decompressed** runtime image (`func_80000450` core1, `func_80019EC0` core2)
  in `boot_hw_stubs.cpp`.
- Dynamic path (host): `func_800815CC` forces overlay table base `0x01F00020`;
  `ovl_load` allocates on the game heap, DMA package, `ovl_clear_bss`, registers
  natives via `load_overlays` at the real text address; `func_80082088` relocates
  entrypoints without PI/cart MMIO.
- O tamanho registrado vem da seção recompilada, não apenas do `text_size` do
  pacote, pois o pacote pode omitir padding/trailing data necessário à seleção
  da seção pelo N64ModernRuntime.
- Relocations curtas e longas são aplicadas. O stream curto é validado antes de
  decidir se usa a chave XOR; `decompressed.us.z64` pode já conter o stream cru.
- Nested syscalls: uma pilha thread-local restaura tanto o alias
  `0x80800000` quanto a base dinâmica usada por `RELOC_*` depois que o callee
  retorna.
- Chamadas ao mesmo overlay ativo reutilizam o pacote para reproduzir os stubs
  autopatcheados do MIPS original. Pacotes residentes (`flag 0x04`) também
  podem ser reutilizados.
- `ovl_unload` explícito sincroniza o mapa nativo e libera pacotes não
  residentes. `defragment_overlays` continua no-op host-safe porque o runtime
  ainda não oferece remapeamento atômico de uma seção movida.
- O evento 3 usa a fila real do scheduler e recebe ACK em `D_80078438`; não é
  mais host-skipped.
- Pacotes comprimidos continuam fora do contrato: o runtime aceita somente
  `decompressed.us.z64` e recusa flag `0x80`.

## Per-overlay data flow

```text
PRELIM_ELF + overlays.us.toml
  -> overlay_processor
   -> overlay_table.s
   -> <name>_header.s (sizes, entrypoints, relocs)
  -> linked into final ELF
  -> rom_compressor packs each overlay in ROM
```

The runtime (in core2) loads an overlay into VRAM, applies its relocs, and
jumps to the requested entrypoint.

## Why recomp cares

For static recomp, `N64Recomp` supports relocatable overlays: each overlay's
functions must be recompiled with the same address mapping and the runtime
must map original VRAM ↔ native function pointers like `RecompFrontend` & the
patch runtime do.
